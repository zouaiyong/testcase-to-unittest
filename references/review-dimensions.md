# 评审维度与子 agent prompt 模板

评审环节**必须**派独立上下文的子 agent（按所在工具选型，见 SKILL.md 阶段 4）。自查抓不出「断言跟着实现走」——
写的时候就是照着实现写的，同一个人再看一遍只会确认自己的偏见。

## 十条评审维度

按「抓出真问题的概率」排序，前 3 条是重点，必须在 prompt 里强调。

| # | 维度 | 具体检查动作 | 典型病症 |
|---|---|---|---|
| 1 | **断言跟着判据走还是跟着实现走** | 逐个检查带 `case` 标记的测试：期望值来源是用例文档的判据原文，还是从生产代码里读出来的？ | 把实现 bug 固化成绿。这是最危险的反模式，测试从此失去发现能力 |
| 2 | **判据明细行是否漏断言** | 每条 TC 的每一行预期都是判据（XMind 版的 `-` 行 / CSV 版「预期结果」列的编号行），逐条核对；带【待确认】的行不算。输出「明细行 N 条 / 已断言 M 条 / 漏了哪几条」 | 用例名声称覆盖，实际只断言了 3 行里的 1 行 |
| 3 | **TC 号引用是否真实且对得上** | 去用例文档里查：①该号是否存在于所声称的那份文件；②标题与预期结果是否真是这个测试在测的东西；③测试类注释声明的覆盖清单与实际是否一致 | 张冠李戴（把 A 用例的判据挂到 B 名下）、类注释虚报覆盖 |
| 4 | **实现不符是否被标成了通过** | 反查有没有断言锁的是当前实现、而不是用例。这类必须改回用例期望并保持失败。禁止建议打 `deviation` 让它变绿 | 把 bug 标绿之后，测试人员看不到失败，开发也不会改 |
| 5 | **数值期望独立手算复核** | 金额/精度/尾差/取整/聚合类断言，评审方**自己算一遍**，逐格比对测试里的字面量 | 只看代码是否自洽 → 算错也发现不了。手算是唯一手段 |
| 6 | **脚手架是否造成系统性假绿** | 默认值选在哪一侧（「查不到」还是「查得到」）；mock 是否让被测逻辑一行未执行；链式 mock 是否吞掉了查询条件 | 全局默认「空」让「本该查到数据」的场景静默走空分支 |
| 7 | **同义反复断言** | 期望值是否 == mock 夹具原值，中间没经过任何被测逻辑加工 | 把生产方法改成硬编码返回夹具值，测试照样绿 |
| 8 | **标记归类与门禁污染** | **实跑**判据门禁。实现不符的失败必须出现在 `case` 且不排除 `impl` 的 Failures 里 | 用 `deviation` 或排除分组把失败从报告里拿掉 |
| 9 | **弱断言** | 「大于 0」该写成「等于 1」；判据写了文案却只断异常类型不断消息；判据没给文案时，没证明拦下它的是这条规则（别的校验也会抛同类异常）；用包含匹配代替逐字比对 | 断言太松，改坏了也不红 |
| 10 | **可测性诚实性** | 用例名 / 注释是否声称验证了实际验不了的东西（如声称验证查询维度，但 mock 方式使条件不可断言） | 空头承诺比不承诺更糟，会让人误以为已有保障 |

## 必须要求评审方实跑

prompt 里明确写：**「自己跑一遍测试并按标记分组核对条数，不许只静态读代码。」**

实跑能抓到静态阅读抓不到的问题。实测案例：评审方靠对比
「全量 72 条」与「判据组 65 条」的差值不合理，才发现标记沿嵌套类叠加导致门禁失效。

## 可直接复用的 prompt 模板

把 `{{...}}` 替换后整体作为评审子 agent 的 prompt（子 agent 类型按 SKILL.md 阶段 4 选）。

```text
你是独立评审方，任务是核对「测试代码里的断言」是否与「功能测试用例文档里的判据」一致。
**只回传文本评审结论，不要修改任何文件、不要落盘。**

## 一、被评审的测试代码（绝对路径）
{{逐个列出测试类与共享脚手架的绝对路径}}

## 二、判据唯一事实源（绝对路径）
{{逐个列出用例文件（md / csv）的绝对路径}}

用例结构（{{按实际格式保留一行，删掉另一行}}）：
- XMind 版：`{{标题层级}} {{编号前缀}}-编号 标题 【优先级】` + 下一级「预期结果」+ `-` 明细行
- CSV 版：「用例编号」「前置条件」「测试步骤」「预期结果」四列，「预期结果」里每个编号行是一条明细

**每一条明细行都是判据，逐条都要核对。** 带【待确认】/【待拍板】/「以实际为准」的行判据未定：
不要求有断言；测试若对这种行写了断言，按维度 1 报（期望值只可能来自代码现状）。

引用约定见 {{约定文件路径}}：测试的类注释、{{用例名注解，如 @DisplayName}}、断言说明必须用
`文件名#编号` 回指用例。

## 三、被测的生产代码（用于判断断言是否真锁住了判据）
{{列出被测类路径与关键方法行号区间}}

## 四、评审标准（按重要性排序，前 3 条是重点）
{{把上面十条维度表逐条粘进来，保留「具体检查动作」与「典型病症」两列}}

## 五、执行要求
1. **必须自己跑一遍测试**，报告全量条数，以及按标记分组的条数
   （{{列出实际门禁命令}}），并做加减核对，指出对不上的地方。
2. 对数值/金额/精度类断言**独立手算复核**，逐格列出「手算值 vs 测试字面量」对照表。
3. 如果某项检查无法完成（文件读不到、命令跑不起来），**明确说明而不是跳过**。

## 六、输出格式（严格遵守）

按文件分组，每条问题一行：

| 严重度 | 文件:行号 | TC 号 | 判据原文（摘录） | 测试里的断言（摘录） | 结论 |

严重度三级：
- 🔴 阻塞：断言与判据矛盾、把实现 bug 固化成绿、TC 号张冠李戴、数值期望算错
- 🟠 重要：判据明细行漏断言、Tag 归类错误、同义反复断言、空头承诺
- 🟡 建议：可读性、命名、注释与判据措辞不一致

表格之后另起三段：
1. **逐 TC 覆盖核对表**：列出所有被声称覆盖的 TC 号，每个标
   「判据明细行 N 条 / 已断言 M 条 / 漏了哪几条」；属前端或【待确认】而不可自动化的行单独标注
2. **失败复核**：列出本次失败里哪些是实现和用例不符（应保持红），哪些是测试写错（必须改回用例期望）
3. **假绿风险清单**：明确指出哪些测试方法存在「即使生产代码算错也依然会绿」的可能，
   并说明触发条件（怎样改坏生产码仍绿）

不要给修改后的代码，不要修改文件。只回传评审文本。
```

## 主 agent 收到评审后的处理规则

| 评审结论 | 动作 |
|---|---|
| 🔴 断言与判据矛盾 / TC 号挂错 / 数值算错 | 立即修，属测试写错 |
| 🔴 判据明细行 0 断言但用例名声称覆盖 | 二选一：补断言，或删掉声称并登记到覆盖缺口 |
| 🟠 同义反复断言 | 换成能验证真实加工的断言；确实验不了就加注释说明局限，不得假装验过 |
| 🟠 标记归类错 | 修正标记，并重跑门禁核对条数 |
| 🟠 维度类判据验不了 | 优先找具名方法用参数捕获器绕过；绕不过就登记缺口 + 删掉空头承诺 |
| 评审发现断言锁的是当前实现、不是用例 | 把断言改回用例期望，让测试失败，并把失败原因写入报告。禁止改开发代码 |
| 评审判定「需业务拍板」 | 只登记到待拍板清单，**不写断言、不进门禁** |

修完必须重跑全量并核对条数，再派复评。
