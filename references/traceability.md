# 引用约定、门禁命令与追溯校验

## 引用约定

写进测试类注释、用例名注解、断言说明三处：

```
<用例目录>/<用例文件>.md#TC-0008
<用例目录>/<用例文件>.csv#TC-0008
```

四条规则及其原因：

| 规则 | 原因 |
|---|---|
| **引用必须带文件名** | 裸 TC 号在多份用例文档间会重复：`testcase-design` 每份用例都从 TC-0001 起编号，跨文件必然重号（实测某项目 5 份用例文档共 304 条，裸号跨文件重复 58 个）。唯一键是「文件名 + TC 号」 |
| **TC 号只能用用例文档里写的那个**（XMind 版在标题开头，CSV 版在「用例编号」列），绝不能用「内容指纹生成 ID」 | 指纹含标题正文与层级名，文档一重排就全量换号，下游引用集体失效 |
| **方法级标记必须自带 `文件名#编号`**，类级标记只用于分组展示 | 类级标记盖多条编号时，校验脚本只能按 1/N 分摊归属，「逐条方法数比对」会退化成小数而失准 |
| **「某条不覆盖」的说明不要写在类级标记行里**，写在对应方法的标记行或普通注释里 | 否定词是**行级**判定，无法把否定范围限定到某一条编号——写在一行会让该行提到的**所有**编号都被判成「声明不覆盖」 |

## 门禁命令

三条测试命令 + 追溯校验 + 脚本自检，用项目实际的构建工具替换：

| 用途 | JUnit5 + Maven surefire 示例 | 其他栈的等价物 |
|---|---|---|
| 全量 | `mvn test` | `pytest` / `npm test` / `go test ./...` |
| 秒级回归（纯口径） | `mvn test -Dgroups=pure` | `pytest -m pure` / `jest -t` / `go test -short` |
| **判据门禁** | `mvn test -Dgroups=case -DexcludedGroups=impl` | `pytest -m "case and not impl"` |
| 失败定位 | 不另跑分组。失败就在全量和判据门禁的 Failures 里，逐条写入报告 | 同 |
| 追溯校验 | `python <skill目录>/scripts/check_tc_refs.py --docs <用例目录> --tests <测试源码目录> --matrix <覆盖矩阵>` | 同（跳语言） |
| 脚本自检 | `python <skill目录>/scripts/check_tc_refs.py --selftest` | 同 |

- 判据门禁**必须**同时带「包含 case」与「排除 impl」。「实现和用例不符」的测试仍带 `case`，必须出现在这次运行的 Failures 里
- 标记会沿嵌套测试结构**叠加**（如 JUnit5 的 `@Nested` 继承外层 `@Tag`）
- 每次执行都要做加减核对：`全量 = 判据门禁（含失败）+ 带 impl 标记的测试`。右边第二项包括纯 impl 和 case+impl 叠加的（叠加的被门禁排除，但不是「纯 impl」，别漏数）。每个测试都该带 `case` 或 `impl` 之一，等式对不上先查有没有两者都没打的。失败条数另记，不从全量里扣掉
- 参数化测试按 1 个方法计；`Tests run` 会把它按数据组展开，所以别拿 `Tests run` 直接和矩阵的预期方法数比

各栈的具体参数与已验证的坑见对应技术栈附录（当前：[java-maven-pitfalls.md](java-maven-pitfalls.md)）。

## 追溯校验脚本

`scripts/check_tc_refs.py` 以「文件名 + TC 号」为唯一键做双向 diff，退出码非零即门禁失败。md 与 csv 用例都认，`--docs` 指向项目里的 `doc/testcases`。

六项检查，1–4 来自用例文档↔测试代码，5 来自覆盖矩阵，6 来自测试方法的标记：

| 项 | 检查 | 级别 |
|---|---|---|
| 1 | 悬空引用（测试引了文档里不存在的编号） | 🔴 门禁 |
| 2 | 裸号引用（分真歧义 / 指向不存在 / 可推断 / 无锚点四级） | 前两级 🔴，后两级告警 |
| 3 | 疑似虚报（只在注释里声称、无用例名声明） | 🟠 告警 |
| 4 | 未覆盖编号（矩阵里标「不覆盖」的不算） | 传 `--matrix` 时 🔴 门禁，未传时统计 |
| 5A | 矩阵标「已写」但无测试引用 | 🔴 门禁 |
| 5B | 已有测试引用但矩阵没登记 | 🔴 门禁 |
| 5C | 矩阵标「已写」但零方法归属 | 🔴 门禁 |
| 5D | 逐条方法数与预期不符 | 🟡 咨询（共享归属会分摊成小数） |
| 5E | 矩阵仍有未收口状态（如 `待写`） | 🔴 门禁 |
| 6 | 仅 impl 覆盖：编号有方法归属，但全是带 `impl` 标记的方法、没有一条 `case` | 🔴 门禁（标记识别是启发式：方法注解块内的标记 + 文件里更靠前的类级标记） |

第 6 项堵的是「按实现写断言、打 `impl`、带上 TC 引用」这条路：门禁排除了它，追溯又认它覆盖了该 TC。报出来的编号要么补 `case` 断言，要么证明全部明细行都未定并移出矩阵。它的粒度是 TC 不是明细行——「给这条 TC 另写一个无关痛痒的 `case` 方法」能骗过脚本，骗不过评审维度 2 的逐行核对。

传了 `--matrix` 时，第 4 项「未覆盖编号 > 0」与第 5E 项「矩阵仍有 `待写` 等未收口状态」直接触发退出码 1，堵住「矩阵留着 `待写` 不改、靠脚本退出码 0 混过阶段 3」的漏洞。但仍要注意：**追溯脚本退出码 0 只是交付的必要条件之一，不等于整份工作通过**——测试运行是否有失败（硬约束 1 的实现不符失败）、独立评审是否通过、单测报告第 1 节是「通过」还是「未完成」，是另外几道独立门禁。

跨语言适配参数：`--tc-prefix` 适配编号格式，`--test-marker` 适配用例名注解，`--test-annotation-pattern` 适配测试方法声明，`--impl-tag-pattern` 适配 impl 标记（默认 `@Tag("impl")`；pytest 用 `pytest[.]mark[.]impl`；项目用常量或元注解时把它们并进正则，不要关掉）。注意 pytest 的 `def test_` 与 Go 的 `func Test` 函数名受语法限制不能含 `.`、`-`、`#`：以它们作为 `--test-marker` 时，必须把 `文件名#TC-编号` 写在该函数声明行的**行尾注释**里（如 `def test_monthly_fee():  # a.md#TC-0001`），或改用自定义装饰器（如 `@tc("a.md#TC-0001")` 并传 `--test-marker "@tc"`）；若写在上一行注释或 docstring 里，会被当成无用例名声明的普通注释而判为「疑似虚报 + 零方法归属」。其余见 `--help`。
