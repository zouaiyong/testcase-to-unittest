# 阶段契约：输入、交付物、完成标准、回退

每阶段都按同一个模式定义。**「完成标准」必须可判定**——能用是/否回答，不能是「基本完成」「差不多了」。
不满足完成标准就不得进入下一阶段；如果发现上一阶段的结论错了，按「回退」栏退回，不要在当前阶段硬凑。

## 总表

| 阶段 | 执行者 | 交付物 | 完成标准（全部满足才算完成） | 不通过时回退到 |
|---|---|---|---|---|
| 入库 | 主 agent | 项目 `doc/testcases/` 中的定稿用例 | 路径由用户给出；只复制定稿用例和评审指引；已列出文件名与 TC 条数；多份需求已问清从哪一份开始 | — |
| 0 探测 | 主 agent | 环境基线表 | 6 项版本查到**具体版本号**；基线命令跑通并记下条数；引擎/依赖缺失已有结论 | — |
| 1 定性 | 主 agent | 四态清单 | 每条用例都有归属且**四态条数之和 = 总条数**；每条阻塞项都附证据 | — |
| 2 拆解 | 主 agent | 覆盖矩阵 | 每条 `可自动化` 都落到**类#方法**；明细行数已逐条数出；预期测试方法数已估算 | 阶段 1（定性判错） |
| 3 实现 | 主 agent | 脚手架 + 测试代码 + 本次运行输出 | 全量 **0 错误 0 跳过**。失败只允许是断言来自用例、实现还没跟上，且必须原样留下；实际条数 = 预期条数；追溯脚本退出码 0 | 阶段 2（落点不存在） |
| 4 评审 | **独立评审子 agent** | 评审报告（6 段齐全）+ 评审记录文件（原文追加） | 🔴 全部有处理结论；🟠 逐条有结论；评审方已自行反查文件、比对用例 hash；复评通过或用满 3 轮 | 阶段 3 |
| 5 交付 | 主 agent | 双清单 + 单测报告 + 门禁命令 + 校验报告 | 失败定位清单三节齐全，每条失败能定位到测试和开发代码；单测报告七节齐全、结论与实测条数一致；用例 hash 与源一致；未覆盖编号 0、矩阵无 `待写`；两份都已落盘 | 阶段 4 |

入库与阶段 0/1/2 的产物**合并落盘为一个文件**（`doc/testcases/{需求名称}-自动化覆盖矩阵.md`，用例来源 / 环境基线 / 四态清单 / 矩阵四节），避免文件散落。

## 用例入库

**输入**：用户给出的功能测试用例目录或文件绝对路径。没有路径时先问，不得开始阶段 1、阶段 2。

**做什么**：

1. 只复制定稿：`{需求名称}-测试用例.md` 或 `{需求名称}-测试用例.csv`，以及同目录的 `{需求名称}-用例评审指引.md` / `{需求名称}-评审指引.md`。
2. 放到项目根下的 `doc/testcases/`。源目录的 `work/`、`_archive` 和其他过程稿不复制。
3. 同一需求 md 与 csv 都有时，先问以哪份为准，只复制这一份和它的评审指引。
4. 复制后列出文件名和每份的 TC 条数。多份需求时问从哪一份开始。文件已经在 `doc/testcases/` 时不要再复制。
5. 算每份用例文件的 sha256，写进 `doc/testcases/{需求名称}-自动化覆盖矩阵.md` 开头的「用例来源」表（这个文件在此时新建，阶段 0/1/2 往后追加）：

   ```markdown
   ## 用例来源
   | 文件 | 源路径 | 源 sha256 | 副本 sha256 | TC 条数 |
   |---|---|---|---|---|
   | 存储费管理-测试用例.md | D:\cases\存储费管理\存储费管理-测试用例.md | 3f2a…9c | 3f2a…9c | 41 |
   ```

   PowerShell：`Get-FileHash -Algorithm SHA256 <文件>`；macOS / Linux：`shasum -a 256 <文件>`。文件本来就在 `doc/testcases/` 的，源路径写「已在库」，只记副本 hash。

   为什么要记：硬约束 2 说判据只读，但副本是本次新增的 untracked 文件，`git status` 看不出它被改过；改副本两个字就能让一条 `case` 断言合法变绿。hash 是唯一能证明「判据从入库到交付没动过」的东西。

**完成标准**：

- [ ] 路径是用户给出的，不是执行者自己猜的仓库外目录
- [ ] `doc/testcases/` 里能看到本次要用的定稿用例，过程稿不在其中
- [ ] 已向用户列出文件名和 TC 条数；多份需求时已确认先做哪一份
- [ ] 「用例来源」表已落盘，每份用例都有 sha256，源与副本 hash 一致

**回退**：无。文件没落定就不得进入阶段 1。

## 阶段 0 · 探测

**输入**：项目根目录、构建配置。

**交付物 · 环境基线表**（写进覆盖矩阵文件「用例来源」之后的第二节）：

```markdown
| 项 | 值 | 对写测试的影响 |
|---|---|---|
| 语言级别 | Java 8 | 不能用 var / records |
| 测试框架 | JUnit Jupiter 5.7.0 | 统一 JUnit5，禁用 JUnit4 写法 |
| Mock 框架 | Mockito 3.6.28 | mockStatic 需额外引 inline 依赖 |
| ORM / 数据层 | MyBatis Plus 3.4.2 | 链式 API 需专门 mock 姿势 |
| 构建测试插件 | surefire 2.22.2 | 支持标记过滤；但过滤器匹配不到嵌套类 |
| 测试引擎完整性 | 无 vintage 引擎 | JUnit4 写法会静默不执行 |
| **基线条数** | **Tests run: 17** | 后续每轮以此为起点做加减核对 |
```

**完成标准**：

- [ ] 6 项都查到**具体版本号**，不接受「较新版本」「应该是 5.x」这类描述
- [ ] 基线命令实际跑过，条数是**从输出里抄的**，不是估的
- [ ] 若发现引擎缺失、依赖缺失、构建插件过旧：已明确结论（补什么 / 不补 / 用什么替代），并写进表里的「影响」列
- [ ] 已查过对应的技术栈附录；没有对应附录的，探测结论要沉淀成新附录

**回退**：无（这是第一阶段）。若连基线都跑不起来，停下来向用户报告环境问题，**不要跳过基线直接写测试**——没有基线数字，后面所有「绿」都无法证伪。

## 阶段 1 · 定性

**输入**：`doc/testcases/` 里已经核对过的定稿用例、被测代码仓库。用例还没入库时退回「用例入库」，不要在这里现找路径。

**交付物 · 四态清单**（覆盖矩阵文件第三节）：

```markdown
| TC 引用（带文件名） | 定性 | 证据 |
|---|---|---|
| 存储费管理-测试用例.md#TC-0007 | 可自动化 | StorageFeeCalcBizService#calcStockBranches L463-481 |
| 存储费管理-测试用例.md#TC-0035 | 仅人工 | 判据全为弹框标题、置灰、按钮文案，无后端落点 |
| 操作费域-测试用例.md#TC-0001 | 无实现-阻塞 | grep "OperateFee\|操作费" src/main → 0 命中 |
| 存储费管理-测试用例.md#TC-0014 | 判据未定-阻塞 | 判据原文：「映射表内容以数据字典为准【待确认】」 |
```

**完成标准**：

- [ ] **每条**用例都有归属，没有「未分类」「待定」这种第五态
- [ ] 四态条数之和 = 用例总条数（做个加法，写出来）
- [ ] 每条 `无实现-阻塞` 都附 **grep 命令 + 命中数**。「看起来没实现」不算证据
- [ ] 每条 `判据未定-阻塞` 都**摘录判据原文**里的待确认字样，指明是哪一行
- [ ] 只有部分明细行未定的用例**没有**被整条阻塞：照常定性，未定行留到阶段 2 的备注里点名
- [ ] 每条 `仅人工` 都说明判据为什么落在前端（控件形态 / 颜色 / 文案展示位置 / 下载交互）
- [ ] `无实现-阻塞` 的用例已单独汇总告知用户，明确「这些现在跑一定全红，属功能未做，不是 bug」

**回退**：无。但本阶段的结论会被阶段 3 校验——如果写测试时发现某条 `可自动化` 其实没有落点，说明这里判错了，**退回本阶段修正定性**，不要在阶段 3 硬写一个测不到东西的测试。

## 阶段 2 · 拆解

**输入**：阶段 1 的四态清单。

**交付物 · 覆盖矩阵**（覆盖矩阵文件第四节）：

```markdown
| TC 引用 | 明细行 | 可自动化行 | 层 | Tag | 落点（类#方法） | 预期方法数 | 状态 | 备注 |
|---|---|---|---|---|---|---|---|---|
| 对账单管理-测试用例.md#TC-0026 | 4 | 4 | 规则层 | case | ReconSvc#addSupplierData | 9 | 待写 | — |
| 对账单管理-测试用例.md#TC-0025 | 2 | 1 | 规则层 | case+impl | ReconSvc#addSupplierData | 8 | 待写 | 第 2 行：人工层（页面表现） |
| 存储费管理-测试用例.md#TC-0013 | 1 | 1 | 纯口径+集成 | case | StorageFeeMetricUtils#monthlyFee | 1 | 部分（真聚合需真库） | — |
```

字段口径：

- **明细行**：XMind 版数「预期结果」下的 `-` 行，CSV 版数「预期结果」列里的编号行，逐条数出来
- **可自动化行**：其中能在本层断言的条数。差值的每一行都要在「备注」里点名原因，只用四类：
  人工层（页面表现）/ 集成层（判据要靠协作方的真实行为才成立，而协作方要真库、真接口，或在本仓库没有实现）/
  判据未定 / 本层原理上验不了。一行同时符合几类时记「判据未定」
- **备注里的原因必须带依据**，口径与阶段 1 的「无实现-阻塞要附 grep」相同。只写类别名的行视为可自动化行，要写断言：

  | 原因 | 备注里要附什么 |
  |---|---|
  | 人工层 | 判据原文里的页面用词（「跳转到」「置灰」「弹出」「Toast」…） |
  | 集成层 | 协作方的 `类#方法`，以及它在本层为什么拿不到真实行为（真库 / 真接口 / 本仓库无实现） |
  | 本层验不了 | 具体的 mock 姿势和被它吞掉的条件（如「`RETURNS_SELF` 链式 mock，`eq(warehouse)` 不可断言」） |
  | 判据未定 | 【待确认】/【待拍板】/「以实际为准」的原文字样 |

  例：`第 3 行：集成层。StockMapper#sumByWarehouse 的聚合要真库，mock 返回值无法证明 SQL 口径`
- **落点**：必须到 `类#方法`，只写类名不算完成——写不出方法名说明还没找到落点
- **预期方法数**：这条 TC 打算写几个测试方法。**阶段 3 靠它做加减对账**，不估就没法核对
- **状态**：`待写` / `已写` / `部分`（部分必须注明缺哪半、为什么）

**完成标准**：

- [ ] 阶段 1 里每条 `可自动化` 的用例都在矩阵中，条数对得上
- [ ] 每条都有 `类#方法` 级落点
- [ ] 明细行数与可自动化行数都填了具体数字，没有留空或写「若干」
- [ ] 每一条「不写断言」的行，备注里都有上表要求的依据，不是只有类别名
- [ ] 层与 Tag 都已定；一条用例跨两层时（如口径层锁公式 + 规则层锁真实调用路径）两层都写
- [ ] 预期方法数已估并求和，**总和写出来**——这就是阶段 3 的验收基准
- [ ] `判据未定-阻塞` 的用例**没有**进矩阵（它们不进门禁）；只有部分行未定的用例照常进矩阵，未定行在备注里写「判据未定」
- [ ] 矩阵**机器可解析**：每节表格自带表头，且表头含「预期方法数」与「状态」两列
      （脚本按列名定位，容忍列序变动与额外列；一份文件里可以有多个分节表格）
- [ ] 「状态」列只用三种值：`待写` / `已写` / `部分`（`部分` 必须注明缺哪半、为什么）；
      确定不做的写 `不覆盖` 并在括号里给原因，脚本会据此把它排除出未覆盖统计

**回退**：写不出落点方法 → 退回阶段 1 重新定性。

## 阶段 3 · 实现

**输入**：覆盖矩阵、阶段 0 的环境基线。

**交付物**：

1. 共享脚手架（测试源码树的公共目录下，一个文件）
2. 分层测试代码（与被测类镜像的目录结构）
3. 一次全量运行的输出（含条数）
4. 追溯校验脚本的输出

**完成标准**：

- [ ] **脚手架先单独验证过**：用它写完 1 个靶子用例并跑绿，才开始铺开。跳过这步 = 每个测试文件重踩一遍坑
- [ ] 全量运行 **0 错误、0 跳过**。失败只允许是「断言来自用例、实现还没跟上」；这类失败必须原样留下。`Skipped` 不为 0 必须解释（有 `@Disabled`？过滤器没匹配上？）
- [ ] 实际测试方法数 = 矩阵预期方法数之和。不等就逐条说明差异原因，**不许默默放过**
- [ ] 每个测试方法的用例名注解都带 `文件名#编号`；裸号只允许出现在注释里
- [ ] 纯口径层的测试**没有**继承/引入规则层的脚手架
- [ ] 没有 spy 被测类、没有 `doReturn/when` 打在被测方法上；mock 只落在协作方
- [ ] 断言都无条件可达：不在 `if` 里、不在可能不执行的回调里；`catch` 块里有 `fail()`
- [ ] 公式类判据的夹具每个因子都是非平凡值且至少两组；能说出「改坏哪一个因子这条会红」
- [ ] 条数加减自洽：`全量 = 判据门禁（含失败）+ 带 impl 标记的测试（纯 impl 与 case+impl 叠加都算）`。失败条数另记，不从全量里扣掉
- [ ] 追溯脚本退出码 0（悬空引用、裸号真歧义、仅 impl 覆盖都是门禁项），且疑似虚报 0。第 6 项有报的，要么补 `case` 断言，要么证明该条全部明细行都未定并移出矩阵；项目用常量或元注解表示 impl 时用 `--impl-tag-pattern` 对齐，不关闭
- [ ] 带 `--matrix` 再跑一次：矩阵对账 A（无虚报已写）、B（无漏登）、C（每条已写编号都有方法归属）三项全绿
- [ ] 归属数之和 == 已归属方法数（脚本自检该不变量，不自洽会直接判 🔴）
- [ ] 用例文档与生产代码**零改动**（用版本控制的 status 证明，不是口头保证）

**回退**：某条用例写不出有效断言 → 退回阶段 2 改落点或改层。发现判据与实现不符 → **不回退、不改断言、不改开发代码**。测试保持失败，到阶段 5 写入失败定位。

## 阶段 4 · 独立评审

**输入**：阶段 3 的全部产物 + 用例文档（副本路径、源路径、入库 hash）+ 覆盖矩阵 + 被测生产代码的绝对路径。被测生产代码的口径是**测试代码 import 的生产类全集，加上这些类直接调用的本仓库类**，不是主 agent 挑出来的「关键方法」——少给一个文件，评审方就看不到那部分实现，判断不了断言是不是照着它写的。

**执行者**：**必须是独立上下文的评审子 agent**（按所在工具选型，见 SKILL.md 阶段 4）。主 agent 自查不算完成本阶段——写的时候就是照着实现写的，自查只会确认自己的偏见。

**交付物**：

1. 评审报告（评审方回传的文本），六段缺一不可：
   1. 问题表（严重度 / 文件:行号 / TC 号 / 判据原文 / 断言摘录 / 结论）
   2. 逐 TC 覆盖核对表（明细行 N 条 / 已断言 M 条 / 漏了哪几条）
   3. 失败复核：哪些失败是实现和用例不符（应保持红），哪些是测试把断言写成了当前实现（必须改回用例期望）
   4. 假绿风险清单（哪些测试「生产代码算错也依然会绿」+ 触发条件，含断言可达性与 spy 被测类）
   5. 数值手算对照表（手算值 vs 测试字面量，逐格）+ 夹具复核（每个因子是否非平凡、改坏哪个因子会红）
   6. 核查声明：用例副本 hash 与源文件比对结果；主 agent 没给但评审方反查到的文件；矩阵里每条「不写断言」的理由逐行成立 / 不成立；无法完成项（读不到的文件、跑不起来的命令——**明确说明，不许静默跳过**）
2. `doc/testcases/{需求名称}-评审记录.md`：主 agent 把每轮评审回传的文本**原样追加**为一节（`## 第 N 轮 · 日期`），不改写、不删节、不加按语。清单 1 从这里摘，不是直接听写。评审原文不落盘，🔴 在转录时就可以消失。

**完成标准**：

- [ ] 派发 prompt 里给了全部绝对路径（含矩阵、用例源路径与入库 hash）+ 10 条评审维度 + 输出格式，并写明「路径是起点不是边界，须从 import 与矩阵反查」
- [ ] prompt 里**明确要求评审方自己跑测试**并按标记分组核对条数、自己算副本 hash 与源比对
- [ ] 评审报告里列出了反查结果（没有漏给就写「无」）；有漏给的文件，主 agent 补上后重新派发，不接受「漏的那部分按常理应该没问题」
- [ ] 评审方报告 hash 不一致 → 停止，先向用户说明副本为何与源不同，不进入修改环节
- [ ] 报告六段齐全；缺段的视为评审未完成，重新派发。评审方声明「跑不起测试」的，先修环境再派，不算一轮
- [ ] 本轮评审原文已追加进评审记录文件，与回传文本逐字一致
- [ ] 🔴 每条都有处理结论：**已修** 或 **明确拒绝并写明理由**（不接受无回应）
- [ ] 🟠 每条都有处理结论
- [ ] 修完**重跑了全量**并核对条数，不是只改代码不跑
- [ ] 复评通过；或已用满 3 轮，此时把未解决项写进交付清单并明确告知用户

**回退**：评审指出断言与判据矛盾 → 阶段 3 把断言改回用例期望，测试保持失败。评审指出判据本身有问题 → 不回退，进阶段 5 的待业务拍板，拍板前不写断言。

> 🔴 循环的终止条件是「评审通过」或「用满 3 轮」，**绝不是「测试变绿」**。

---

## 阶段 5 · 双清单 + 单测报告

**输入**：阶段 4 的评审报告、阶段 2 的覆盖矩阵、全量与门禁的命令输出、本分支改动代码的覆盖率输出、追溯脚本输出。

**交付物**：

| 清单 | 给谁 | 落盘位置 | 处理方向 |
|---|---|---|---|
| 1 · 测试缺陷清单 | 写测试的人 | 评审报告内即可 | **改到评审通过** |
| 2 · 失败定位清单 | 测试定位、开发改实现 | 用例目录说明文件的独立小节 | **不许改断言或开发代码把这些失败变绿** |
| 3 · 单测报告 | 看结果的人 | 用例目录 `{需求名称}-单测报告.md` | 每次执行**整份重写**，反映本次 |

清单 2 必须三节齐全：

```markdown
### 当前失败（N 条）
| # | 用例 | 用例要求 | 本次实际 | 失败测试 | 断言位置 | 开发代码位置 | 原因 |
|---|---|---|---|---|---|---|---|
| 1 | xxx.md#TC-00NN | 「用例原文」 | 命令输出里的 expected / but was | 类#方法 | 测试文件:行号 | 生产文件:行号 | 一句话，测试能据此定位 |

### 待业务拍板（N 条，拍板前不写断言）
| # | 用例 | 争点 |

### 已知覆盖缺口
- 本层原理上验不了的判据（写清是什么限制导致的）
- 需真库的部分
- 需人工的部分
```

单测报告七节，按这个模板写，空节写「无」不能省：

```markdown
# {需求名称} 单测报告

## 1. 结论
通过 | 未完成
（一句话：本次测了什么、结果是什么。有失败时写失败条数，不写通过）

## 2. 范围
| 项 | 值 |
|---|---|
| 用例文件 | |
| 被测代码 | |
| 基线 → 本次全量 | Tests run: N → M |

## 3. 执行结果
- 命令：`…`
- 从输出抄：Tests run / Failures / Errors / Skipped
- 方法数：预期 X / 实际 Y（按测试方法计，不按展开后的 Tests run）

## 4. 覆盖
- 四态：可自动化 a + 仅人工 b + 无实现-阻塞 c + 判据未定-阻塞 d = 总数
- 明细行：共 N，已断言 M，不可单测 K（人工层 / 集成层 / 判据未定 / 本层验不了，各几条）
- 未覆盖编号：列出，或写 0

### 代码覆盖率
紧接在上面三条后面，不另起「第 8 节」，第 5 节仍是门禁。

- 命令、工具版本、Tests run / Failures / Errors / Skipped，从本次输出抄
- 口径：当前分支相对基线（默认 `origin/master`，`base...HEAD`）里、**本需求**改过的可执行行。基线未改文件、同一分支的其他需求，都不进分母
- 主数字：行覆盖率 = 已覆盖 / 可执行。失败用例执行过的行算已覆盖
- 类表：类名、已覆盖 / 可执行、行覆盖率、未覆盖落在哪些方法
- 大段为 0 时写原因（用例范围不测 / 这层进不去 / 只测到私有方法）。用例写明不测的，不要为了覆盖率去补测试

## 5. 门禁
| 用途 | 命令 | 条数 |
|---|---|---|
| 全量 | | |
| 纯口径 | | |
| 判据门禁 | | |

加减：全量 = 判据门禁（含失败）+ 带 impl 标记的测试 → 对得上 / 对不上（差在哪）。失败条数另记，不从全量里扣掉。

## 6. 失败定位
没有失败就写「无」。有失败则每条都写，测试人员不看命令行也能定位：

| # | 用例 | 失败测试 | 断言位置 | 用例期望 | 本次实际 | 开发代码位置 | 原因 |
|---|---|---|---|---|---|---|---|

期望和实际从本次测试输出抄，不要改成和实现对齐之后的值。开发代码位置写到文件和行号。待业务拍板、已知缺口若有，另起一段，写清单路径。

## 7. 追溯与评审
- 判据完整性：每份用例副本的 sha256 与源文件一致 / 不一致（不一致写出哪份）；评审方独立比对的结果
- 追溯命令与退出码；悬空引用、虚报已写、仅 impl 覆盖各几条；未覆盖编号几个（写「通过」要求为 0）
- 矩阵状态统计：已写 / 部分 / 不覆盖各几条，`待写` 必须为 0
- 评审第几轮通过；用满 3 轮仍未解决的 🔴 写文件:行号。没有就写「无」
```

结论按顺序判定，命中即停：

1. 有失败、错误或跳过，或追溯退出码非 0，或仍有未解决 🔴，或还有【待确认】未拍板 → **未完成**
2. 追溯第 4 项未覆盖编号不为 0，或矩阵里还有 `待写` / 未经评审复核的 `不覆盖` → **未完成**（难写的 TC 留着不写，不能换来通过）
3. 任一用例副本 hash 与源文件不一致 → **未完成**
4. 否则 → **通过**

失败若是实现和用例不符，结论仍是「未完成」，第 6 节必须能定位。不得因为失败「意料之中」就写成通过。

**完成标准**：

- [ ] 清单 2 三节齐全。当前失败的条数 = 本次运行里「断言来自用例、实现未跟上」的 Failures 条数
- [ ] 每条失败都有用例要求、本次实际、失败测试、断言位置、开发代码位置、一句话原因。缺一列不算能定位
- [ ] 没有任何一条失败被改成锁当前实现，也没有为这些失败改过开发代码
- [ ] 清单已落盘到用例目录说明文件，且测试代码注释里对它的引用**不悬空**
- [ ] 全量、纯口径、判据门禁都实测跑过，给出具体条数，并做加减核对。实现不符的失败必须出现在全量和判据门禁的 Failures 里
- [ ] 追溯脚本（含 `--matrix`）已跑，退出码写进单测报告第 7 节；非 0 时结论只能是「未完成」；第 4 项未覆盖编号为 0，否则结论只能是「未完成」
- [ ] 重新算了 `doc/testcases/` 里每份用例的 sha256，**与源文件**比对（源不可达时与入库记录比对并注明），结果写进第 7 节；不一致 = 判据被改，结论只能是「未完成」，并把 diff 原样交给用户
- [ ] 评审记录文件里每轮评审原文齐全，清单 1 的每条都能在其中找到出处
- [ ] `--selftest` 通过（脚本自身的编号展开与表格解析回归）
- [ ] 覆盖矩阵的「状态」列已从 `待写` 更新为 `已写` / `部分`，矩阵与实际一致
- [ ] 单测报告已落盘到用例目录，文件名 `{需求名称}-单测报告.md`，七节齐全
- [ ] 第 4 节用例覆盖之后有「代码覆盖率」：本分支、本需求改动代码的行覆盖率，以及按类的未覆盖位置。数字从本次覆盖率命令抄，不是整仓百分比
- [ ] 报告里的条数、退出码都是从本次命令输出抄的，每节能对上对应命令
- [ ] 结论只有通过或未完成，与第 3、6 节的失败条数一致。有失败时不写「通过」
- [ ] 生产代码与用例文档零改动（版本控制 status 为证；单测报告与清单是本次新增，不算改用例）

## 增量执行（不是从零开始时）

已有部分测试、只补一批用例时：

| 阶段 | 能否复用上次结论 |
|---|---|
| 0 | 版本表可复用，但**基线条数必须重测**（代码可能已变） |
| 1 | 只对新增/变更的用例定性；但要复核旧的 `无实现-阻塞` 是否已经实现了 |
| 2 | 在既有矩阵上追加行，不重建；**预期方法数总和要重算** |
| 3 | 复用既有脚手架；若新用例需要新的 mock 姿势，扩脚手架而不是在测试类里各写一遍 |
| 4 | **不可跳过**。增量改动同样要独立评审 |
| 5 | 失败定位清单按本次运行重写。开发把实现改到和用例一致后，对应失败从清单消失，测试自然变绿，不要提前改断言。单测报告按本次执行**整份重写** |

> 增量场景最容易出的问题：旧的 `无实现-阻塞` 用例其实已经实现了，但没人回头改定性，
> 于是那批用例永远躺在「待开发」里不被测试。每次增量执行都要扫一遍旧的阻塞项。
