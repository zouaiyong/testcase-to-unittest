# testcase-to-unittest

把已经定稿、带 TC 编号的功能测试用例，落成可追溯的自动化单测。断言只来自用例判据；实现和判据不一致时测试保持失败，失败原因写进报告，交给开发改实现。

这个 skill 要拦住的是「测试把自己改绿」：不改断言迁就实现，不改开发代码让测试通过，不用分组或标记把失败从报告里拿掉。

给 agent 执行用的完整规则在 [SKILL.md](SKILL.md)。本文件只说明这个仓库是什么、怎么装、什么时候用、产物落在哪。

![skill 全景图](skill全景图.png)

## 什么时候用

用户要「写单测 / 补单测 / 对着用例把能单测的写成单测」，要核对断言是否和用例判据一致，或要建立「TC 号 → 测试」的追溯门禁时使用。

前提有两条：用例已经定稿，被测实现已经存在。

| 适用 | 交给别的 skill 或不要做 |
|---|---|
| 用例是 Markdown 或 CSV，每条有稳定 TC 号 | 用例还没写 → `testcase-design` |
| 被测代码已在仓库里，要补自动化 | 要评审用例写得好不好 → `testcase-closed-loop` |
| 要核对「断言 ↔ 判据」 | 只要把定稿用例转成 Excel |
| 要建立 TC 号到测试的追溯门禁 | 探索性测试、性能测试、UI 自动化、真库集成脚本 |

流程与约束和语言、框架、业务域无关。框架特有的标记、断言 API、mock 姿势和构建命令放在技术栈附录。当前附录是 Java / Maven / JUnit 5 / Mockito / MyBatis Plus；碰到新栈，按阶段 0 探测后新建同格式附录。

## 定性后的三条出路

每条用例先定性，再走对应出口。没给用例路径，或同一需求的 md 和 csv 都在、还没选定以哪份为准，先停下来问。用例入库并记下 sha256 之后，阶段 0 的环境探测可以并行。

| 出路 | 判定 | 做什么 |
|---|---|---|
| 不归单测 | 判据落在人工层或集成层 | 只登记缺口。备注点名原因并附可核对依据。不写页面自动化，不写真库 / 真接口脚本 |
| 整条阻塞 | 找不到实现，或判据整条未定 | 不进覆盖矩阵，不当 bug。清单里说明是等实现还是等业务拍板 |
| 可自动化 | 纯口径层或规则层能断言 | 先写覆盖矩阵（落到类#方法），再写单测。缺几行也进矩阵，缺的行单独注明原因 |

四态用词：`可自动化` / `仅人工` / `无实现-阻塞` / `判据未定-阻塞`。部分明细行未定的，整条仍可定性，未定行不计入可自动化行，登记为待业务拍板。

分层按被测对象的依赖半径切，半径越小越先做。本 skill **只产出前两层的代码**：

| 层 | 依赖 | 测什么 |
|---|---|---|
| 纯口径层 | 无，纯函数 | 公式、精度、量纲、舍入、尾差、取整、聚合口径、判定真值表 |
| 规则层 | Mock，不起容器、不连库 | 拦截门槛、状态流转、幂等、校验顺序、提示文案、交互调用 |
| 集成层 | 真库 / 真接口 | 只登记缺口，不写脚本 |
| 人工层 | 浏览器 | 只登记缺口，不写脚本 |

标记可叠加：`pure`（零 mock）、`case`（判据来自用例）、`impl`（用例没写、断言来自实现）。`impl` 不能拿来覆盖用例里已经写明的判据。

## 流程

```
用例入库 → 阶段0 探测 → 阶段1 定性 → 阶段2 拆解 → 阶段3 实现 → 阶段4 独立评审 → 阶段5 交付
```

| 阶段 | 谁做 | 交付 |
|---|---|---|
| 入库 | 主会话 | 定稿用例进入项目 `doc/testcases/`，记下源路径和 sha256 |
| 0 探测 | 主会话 | 语言、测试框架、mock、ORM、构建插件、测试引擎的具体版本，以及基线测试条数 |
| 1 定性 | 主会话 | 每条 TC 的四态归属；阻塞项附证据 |
| 2 拆解 | 主会话 | 覆盖矩阵：层、Tag、类#方法、预期测试方法数 |
| 3 实现 | 主会话 | 先脚手架，再用一条靶子用例验证，然后按矩阵铺开 |
| 4 评审 | 独立上下文的子 agent | 只挑刺，不改文件。主会话只修测试缺陷。最多 3 轮 |
| 5 交付 | 主会话 | 双清单 + 七节单测报告。结论只有「通过」或「未完成」 |

阶段的输入、模板、完成标准和回退见 [references/stage-contracts.md](references/stage-contracts.md)。不满足完成标准不得进入下一阶段。落点对不上时退回定性，不在实现阶段硬凑。

评审循环的终止条件是「评审通过」或「用满 3 轮」，不是「测试变绿」。判据和实现不符的失败保持红色：禁止改断言，禁止改开发实现。3 轮后仍有必须处理的问题，写进交付清单并明确告诉用户。

## 四条硬约束

完整表述以 [SKILL.md](SKILL.md) 为准。

1. 红的原因是判据和实现不符时，保持失败并写入报告。禁止改断言、禁止改开发实现、禁止用标记把失败排除出报告。
2. 判据文件对写单测的人只读。认为判据错了就停下来问。用例要更新只能重新入库、换 sha256 基线，不能直接改副本。
3. 权威源顺序：已定稿的用例原文 > PRD / 需求原文 > 仓库里开发侧整理的需求文档。不用开发侧文档判定人工用例写错了。
4. 门禁看命令的非零退出码和实际跑起来的条数（`Tests run: N` / `N passed`）。过滤器匹配不到测试时会出现「0 条且构建成功」，这是假绿。

## 安装

仓库根目录要有 `SKILL.md`。克隆到 agent 会扫描的 skills 目录，目录名保持 `testcase-to-unittest`。

用户级（本机所有项目都能触发）：

```powershell
git clone https://github.com/zouaiyong/testcase-to-unittest.git "$env:USERPROFILE\.agents\skills\testcase-to-unittest"
```

```bash
git clone https://github.com/zouaiyong/testcase-to-unittest.git ~/.agents/skills/testcase-to-unittest
```

Claude Code 使用 `~/.claude/skills/testcase-to-unittest`。只想在某一个代码仓库里启用时，克隆到该仓库的 `.agents/skills/testcase-to-unittest`。

追溯脚本需要 Python 3，无第三方依赖：

```bash
python scripts/check_tc_refs.py --selftest
```

## 怎么开始一轮

对已经加载本 skill 的 agent 说明两件事：

1. 定稿功能用例的路径（`{需求名称}-测试用例.md` 或 `.csv`）。
2. 被测代码所在的项目。

消息里没有用例路径时，agent 应先问，不应自己到仓库外查找，也不应先读实现再拆用例。同一需求 md 和 csv 都有时，先确认以哪份为准。

入库只复制定稿用例和同目录的评审指引到被测项目的 `doc/testcases/`。`work/`、`_archive` 等过程稿不复制。每份用例记下源路径和 sha256，作为本次执行的判据基线。

## 写进被测项目的产物

这些文件落在**被测项目**里，不在本 skill 仓库里。

| 产物 | 位置 |
|---|---|
| 覆盖矩阵（用例来源、环境基线、四态清单、矩阵） | `doc/testcases/{需求名称}-自动化覆盖矩阵.md` |
| 评审记录（每轮原文只追加） | `doc/testcases/{需求名称}-评审记录.md` |
| 单测报告（七节） | `doc/testcases/{需求名称}-单测报告.md` |
| 失败定位清单 | 用例目录说明文件中的独立小节，并抄进报告第 6 节 |
| 共享脚手架与分层测试 | 被测项目的测试源码树 |

单测报告结论只有两档：

- **通过**：全量 0 失败、0 错误、0 跳过；追溯退出码 0 且未覆盖编号为 0；矩阵没有 `待写`；用例副本 hash 与入库基线一致；没有未解决的必须修改项；没有待拍板项。
- **未完成**：上面任一条件不成立。有失败就写未完成，并逐条写到测试人员能找到用例、测试方法和开发代码。

## 追溯门禁

测试里引用用例必须写成 `文件名#TC-0008`。裸 TC 号会在多份用例之间重复，不能当唯一键。

在被测项目里执行：

```bash
python <skill目录>/scripts/check_tc_refs.py \
  --docs doc/testcases \
  --tests <测试源码目录> \
  --matrix doc/testcases/<需求名称>-自动化覆盖矩阵.md
```

脚本做六项检查：悬空引用、裸号引用、疑似虚报、未覆盖编号、矩阵对账、仅 `impl` 覆盖。退出码 `0` 表示门禁通过，`1` 表示门禁失败，`2` 表示参数或读取错误。编号前缀、用例名标记、测试方法声明可以用参数适配 pytest、Jest、Go 等，见 `python scripts/check_tc_refs.py --help` 和 [references/traceability.md](references/traceability.md)。

判据门禁必须同时包含 `case`、排除 `impl`。实现不符的测试仍带 `case`，必须出现在这次运行的失败列表里。每次执行做加减核对：全量条数 = 判据门禁（含失败）+ 带 `impl` 标记的测试。

Windows PowerShell 下管道可能把中文输出解错。先执行 `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`，或加上 `--out report.txt` 把结果写成 UTF-8 文件。
