# testcase-to-unittest

[![skills.sh](https://skills.sh/b/zouaiyong/testcase-to-unittest)](https://skills.sh/zouaiyong/testcase-to-unittest)

把已定稿、带 TC 编号的功能测试用例落成自动化单测。断言只来自用例判据；实现不符时测试保持失败，交给开发改实现。不改断言，不改开发代码。

用例还没写用 `testcase-design`。前提是用例已定稿、实现代码已存在。执行规则在 [SKILL.md](SKILL.md)。

![skill 全景图](skill全景图.png)

## 流程

先收用例，再往下走。没给用例路径就停下来问。同一需求的 md 和 csv 都在时，先问以哪份为准。阶段 0 可以和入库并行。每阶段的完成标准在 [references/stage-contracts.md](references/stage-contracts.md)，不满足不得进入下一阶段。

| 阶段 | 做什么 |
|---|---|
| 入库 | 把定稿用例和评审指引复制到被测项目的 `doc/testcases/`，记下源路径和 sha256。这是本次执行的判据基线。用例中途更新只能重新入库换基线，不能直接改副本 |
| 0 探测 | 记下语言、测试框架、mock、ORM、构建插件、测试引擎的具体版本，跑一次基线并记下测试条数 |
| 1 定性 | 每条 TC 对上代码落点，归入四态：`可自动化` / `仅人工` / `无实现-阻塞` / `判据未定-阻塞`。找不到实现要用检索证明，不当 bug |
| 2 拆解 | 可自动化的用例定层、定 Tag、落到类#方法，写成覆盖矩阵。不写断言的行要附依据 |
| 3 实现 | 先搭脚手架，用一条判据明确的靶子用例验证，再按矩阵铺开。引用写成 `文件名#TC-0008` |
| 4 评审 | 独立子 agent 只挑刺，主会话只改测试缺陷。最多 3 轮。停在「评审通过」或「用满 3 轮」，不停在「测试变绿」 |
| 5 交付 | 测试缺陷清单、失败定位清单、七节单测报告。结论只有「通过」或「未完成」 |

定性后三条出路：

- **不归单测**：人工层、集成层只登记缺口，不写页面自动化，不写真库脚本。
- **整条阻塞**：无实现，或判据整条未定。不进矩阵，等实现或业务拍板。
- **可自动化**：纯口径层（纯函数、公式、精度）和规则层（Mock，不起容器、不连库）写单测。本 skill 只产出这两层的代码。

判据和实现不符时测试保持失败：禁止改断言，禁止改开发实现，禁止用标记把失败排除出报告。四条硬约束的完整表述在 [SKILL.md](SKILL.md)。

入库到拆解的结论合在一份覆盖矩阵里，评审和报告另开文件。各份写什么见下方「交付物」。

## 安装

```bash
npx skills add zouaiyong/testcase-to-unittest
```

会装到 `~/.agents/skills/testcase-to-unittest`。WorkBuddy、Claude Code 不读这个目录，装完后让对应 Agent 把该路径软链接到自己的 skills 目录（WorkBuddy：`~/.workbuddy/skills/testcase-to-unittest`；Claude Code：`~/.claude/skills/testcase-to-unittest`）。Windows 建不了软链接就用目录联接。链好后新开一轮对话即可被发现。

也可以把本仓库直接放到上述目录。目录里必须有 `SKILL.md`。

## 怎么用

对已经加载本 skill 的 Agent 说「写单测」「补单测」或「对着用例把能单测的写成单测」，并给两样东西：

1. 定稿功能用例的路径：`{需求名称}-测试用例.md` 或 `{需求名称}-测试用例.csv`（`testcase-design` 的两种产物都能读）。
2. 被测代码所在的项目。某条 TC 找不到代码落点时记成 `无实现-阻塞`，不当 bug。

没给路径时 Agent 会先问，不会自己到仓库外翻，也不会先读实现再拆用例。同一需求 md 和 csv 都有时，先确认以哪份为准，只入库这一份和它的评审指引。`work/`、`_archive` 等过程稿不复制。

已经有一部分单测、只补一批时，直接说补哪几条或哪个模块。用例在执行过程中改了，告诉 Agent「用例更新了」：它会重新复制、追加一条 sha256 基线，受影响的 TC 回到定性，不会在副本上直接改判据。

Agent 只写纯口径层和规则层的测试。页面跳转、颜色、Toast，以及必须连真库、真接口才能成立的判据，登记成缺口，不写自动化脚本。判据和实现不一致时，测试保持失败，原因写进报告，交给开发改实现。

测试里引用用例写成 `文件名#TC-0008`。交付前 Agent 会跑追溯校验，退出码非 0 时报告结论只能是「未完成」：

```bash
python <skill目录>/scripts/check_tc_refs.py --docs doc/testcases --tests <测试源码目录> --matrix <覆盖矩阵>
```

## 交付物

都落在**被测项目**里，不在本 skill 仓库。

| 产物 | 位置 | 给谁看 |
|---|---|---|
| 分层测试代码 | 与被测类镜像的测试目录；公共脚手架单独放 | 跟着构建跑 |
| 自动化覆盖矩阵 | `doc/testcases/{需求名称}-自动化覆盖矩阵.md` | 看这次基线、环境、四态和每条 TC 落在哪 |
| 评审记录 | `doc/testcases/{需求名称}-评审记录.md` | 每轮评审原文只追加，不改写 |
| 失败定位清单 | 用例目录说明文件里的独立小节，并抄进报告第 6 节 | 测试定位、开发改实现。不许为了变绿去改断言 |
| 单测报告 | `doc/testcases/{需求名称}-单测报告.md` | 看这次结果。七节缺一不可，空节写「无」 |

覆盖矩阵四节：用例来源（含 sha256 基线）、环境基线、四态清单、矩阵（层、Tag、类#方法、预期方法数）。

失败定位清单三节：当前失败、待业务拍板（拍板前不写断言）、已知覆盖缺口。

单测报告七节：

1. **结论**：只有「通过」或「未完成」。有失败就写未完成。
2. **范围**：用例文件、被测代码、基线条数到本次全量。
3. **执行结果**：命令，以及从输出抄来的 Tests run / Failures / Errors / Skipped。
4. **覆盖**：四态条数、明细行认领情况、未覆盖编号；接着写本需求改动代码的行覆盖率。
5. **门禁**：全量、纯口径、判据门禁三条命令的条数，并做加减核对。
6. **失败定位**：每条写到用例、测试方法、期望、实际、开发代码位置。
7. **追溯与评审**：副本 hash 是否仍等于入库基线，追溯脚本退出码，未解决的评审问题。

「通过」要同时满足：全量 0 失败、0 错误、0 跳过；追溯退出码 0 且未覆盖编号为 0；矩阵里没有 `待写`；副本 hash 与入库基线一致；没有未解决的必须修改项；没有待拍板项。差一条就是「未完成」。回复里给结论和报告路径，报告全文留在文件里。
